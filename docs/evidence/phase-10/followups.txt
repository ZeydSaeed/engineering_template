does not hold. A disposable GitHub runner is a separate machine with its
own servers and nothing to harm.

Batch D: load on a Linux server, direct and through PgBouncer (part of item 5)
-------------------------------------------------------------------------------

operations.yml job "load" (run 43570998096, commit f22e397): the release
built and deployed with the real scripts on an ubuntu-latest runner (4
vCPU) prepared by server-setup.sh with PostgreSQL 18 (APP_DB=pgsql), PHP-
FPM 8.5 static 16 workers, Nginx over HTTPS; 300 synthetic users, 20,000
audit records, 10,000 requests (PerformanceSeeder, RequestsPerformanceSeeder);
k6 2.2.0 in the pinned image on the same runner. One run each; thresholds
off, the error rate reported.

| Scenario (VUs)              | Set-up    | Requests | req/s | Non-200 | Checks    | p50 / p95     | app p50 | db p50 / p95  |
| --------------------------- | --------- | -------- | ----- | ------- | --------- | ------------- | ------- | ------------- |
| baseline (30 visitors + 20) | direct    | 3,099    | 17.7  | 1.87 %  | 5980/6038 | 8 / 27 ms     | 8 ms    | 0 / 14 ms     |

| requests (20 + 5 approvers) | pgbouncer | 1,593    | 9.1   | 0.44 %  | 1742/1742 | 17 / 21 ms    | 11 ms   | 6 / 7 ms      |

(db p50 0 ms in baseline: most of its requests are the guest pages, which
read nothing from the database.)

Reading
- Every non-200 answer was 429 from Nginx's per-client limit (zone
  template_requests, 20 r/s, burst 40; error.log "limiting requests"):
  all virtual users share one address here. On the server the limit
  works; the failures are not errors of the application.
- PgBouncer halves database time per request (12 to 6 ms p50 in the
  requests scenario) and cuts its latency p50 from 25 to 17 ms; throughput
  is set by the scenarios' think time, so it does not change.
- The same scenarios on the Windows laptop (Phase 9) took p50 989 ms and
  5.83 s: the laptop's connection set-up and shared CPU, not the
  application. These Linux figures are still one runner with the load
  generator on it: a comparison of set-ups, not a capacity.

Defects found on the way (in the measurement, not the application)
- The PostgreSQL 18 server could not be installed over the runner's
  libpq-dev (the pg_config conflict): libpq-dev is removed first.
- The k6 container could not write its summary (folder permissions).
- The scripts' 1 % failure threshold stopped the run at the 429s; CI now
  measures to the end and reports the rate.

Batch E: an active ZAP scan, signed in (part of item 5)
-------------------------------------------------------

operations.yml job "zap-signed-in" (scripts/ci/zap-signed-in.sh): the
release on a CI runner from the deploy/ templates; an administrator with
an authenticator secret (PerformanceSeeder); sign-in with password and
TOTP; ZAP 2.17.0 (pinned) zap-full-scan with the session on every request
(replacer), the AJAX spider (a real browser: the Inertia pages' links are
in page data), the sign-out address excluded, the active scan capped at 20
minutes and paced under Nginx's per-client limit. Fails on any High alert.

Runs
- 5841cf4: the classic spider reached only /dashboard (links rendered by
  JavaScript): the job failed on its own coverage check ("the session did
  not hold"); fixed with the AJAX spider.
- 0bf773c: 18 signed-in paths reached; 1 High: "SQL Injection (High,
  Medium confidence)" on /requests; ZAP's parameter and payload were not
  printed then.
- Investigation: every parameter of the list is checked against its list
  of allowed values or bound (search: LIKE with a bound pattern and
  ESCAPE; sort and filters: allow-lists; paging: integers). A new test,
  tests/Feature/Requests/RequestsTableInjectionTest.php, sends 9 classic
  payloads in the search and 7 in sort, direction, filters and paging:
  17/17 on SQLite and PostgreSQL, each treated as data (no extra rows, no
  error). The scan now prints the parameter, attack and evidence of any
  High alert.
- 4cd3a18: 20 signed-in paths reached (/admin/reports, /admin/users,
  /admin/users/invite, /dashboard, /notifications, /requests,
  /requests/new, /settings/appearance, /settings/documents,
  /settings/profile); 0 High alerts. The SQL injection alert did not come
  back. Verdict: a likely false positive (ZAP infers boolean or timing
  differences; different search texts give different rows), not proven,
  since its evidence of the first run was not kept; the tests and the code
  show no injection path.

Alerts of the signed-in scan (all below High), with what they mean
- 10055 CSP style-src unsafe-inline: the accepted residual risk (ADR-0016).
- 10010 Cookie no HttpOnly: XSRF-TOKEN, read by the page by design.
- 10044 Big redirect, 10015/10049 cache directives, 10109, 10112, 120000:
  as classified in .zap/rules.tsv for the baseline scan.
- 10024 Information in URL, new signed in: /admin/users?user=1, the user
  table's side panel keeps the person's internal id in the address. Low
  risk (an administrator's own page), but it departs from the template's
  rule that internal ids stay out of URLs (Requests use UUIDs). Proposed:
  the panel addresses people by a UUID. Not changed in this batch.
